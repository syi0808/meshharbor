# QuadriFlow package preparation

This is preparatory evidence tooling, not a released package. CLI, REST, MCP, and Studio expose backend status and a guarded installation request, but the request currently fails closed; it is not a usable download/install workflow.

The pinned upstream source is `hjwdzh/QuadriFlow` at `810b7a0967c35b0dc85b4464e3835e26a756c967`. The approved candidate run [#43721747855](https://github.com/syi0808/meshharbor/actions/runs/43721747855) completed all three primary/independent build-pair checks and generated signed, temporary candidates with passing fresh signature-verification jobs. Linux and macOS exact-signed-digest synthetic-cube jobs also passed MeshHarbor's core output validator ([Linux](https://github.com/syi0808/meshharbor/actions/runs/43721747855/job/132848222187), [macOS](https://github.com/syi0808/meshharbor/actions/runs/43721747855/job/132848222186)). The original Windows native job failed its material check before execution; a later read-only [Windows verification run #43731453754](https://github.com/syi0808/meshharbor/actions/runs/43731453754) verified and executed the same original signed artifact on the synthetic cube, without running the MeshHarbor core output validator. The initial candidate run therefore remains an overall failure, and its results are not a trusted distributable package or an installer.

The release manifest currently contains no artifacts. The public CLI/REST/MCP/Studio install route checks a release-verification gate before calling the lower-level transactional installer. With the current empty manifest, install requests do not download, create a QuadriFlow backend directory, or install anything. The lower-level installer supports future uncompressed POSIX USTAR packages with bounded system-curl downloads, strict member/path checks, SHA-256 verification, owner-private staging, immutable versions, atomic activation markers, and explicit rollback; fake-downloader tests do not access the network or execute QuadriFlow.

A future package needs an exact source and workflow commit, per-platform archive and payload checksums, complete third-party notices, an independently validated SBOM, and verifiable provenance/signature material. The product now verifies a manifest-pinned Sigstore bundle and its signed SLSA source/material policy before issuing the installer capability. A hash-pinned or provenance-verified artifact is not legal clearance or release approval. The manual candidate workflow's attestation applies only to the executable; it does not attest a complete install archive or prove dependency closure, license compliance, or release approval. The candidate workflow therefore cannot populate the release manifest by itself.

## Manual candidate build and attestation (not a release)

`.github/workflows/quadriflow-candidate-build.yml` has only a `workflow_dispatch` trigger. A maintainer must choose the main branch and check `confirm_candidate`; jobs on other refs or without the explicit input are skipped. For every target platform the workflow invokes `.github/workflows/quadriflow-candidate-build-reusable.yml` from two distinct named caller jobs (`primary` and `independent`) on separate unprivileged GitHub-hosted runners. Both fetch the pinned upstream source and use the same checked-in build recipe; the recipe sets `SOURCE_DATE_EPOCH`, `TZ`, `LC_ALL`, `LANG`, and `ZERO_AR_DATE` for the native compile. Neither build job has signing credentials or executes the generated executable. Each build exposes the immutable artifact ID returned by `actions/upload-artifact` as its caller-job output. The isolated signer downloads by those exact IDs rather than artifact names, checks expected replica labels and fail-closed metadata, and hashes both regular executable files. It refuses to sign unless the digests match exactly; deleted/recreated artifacts have different IDs and cannot silently replace the outputs selected by those job outputs. The signed SLSA predicate records that two-job strategy and the independently observed digest; the Rust verifier requires that digest to equal the signed executable subject. A separate GitHub-hosted job checks out the exact same workflow commit, downloads the candidate without executing it, verifies the local bundle with the runner-provided GitHub CLI, and uploads verified temporary evidence with seven-day retention. This keeps build tools and changes made by compiling upstream code out of the signer and verifier jobs. The verifier trusts the GitHub-hosted runner image and its preinstalled `gh` binary; the script checks the CLI version but does not independently hash that binary. It does not create a GitHub Release or write to the product manifest. The attestation itself is stored by GitHub as public repository metadata.

`scripts/quadriflow_attestation_verify.py` invokes the clean verifier job's GitHub CLI without a shell and fails closed unless the verified output matches the fixed policy: MeshHarbor's repository and numeric IDs, `refs/heads/main`, exact source and workflow commits, the candidate workflow path, the GitHub Actions OIDC issuer, a `workflow_dispatch` trigger, GitHub-hosted runner, SLSA provenance v1, and the executable's SHA-256 subject. It obtains the Sigstore trusted-root JSONL through `gh attestation trusted-root` (TUF-verified by the CLI), uses it only for the local bundle verification, and additionally checks the CLI's certificate and statement summary before retaining the bundle. The CLI must be version 2.96.0 or newer in the 2.x series. Unit tests mock all CLI invocations; they test command-policy construction and rejection logic, but do not cryptographically verify a bundle or check the trust root offline. The candidate workflow itself performs real Sigstore verification on the hosted runners, but this evidence cannot mint the product's in-process installer capability. Candidate run [#43721747855](https://github.com/syi0808/meshharbor/actions/runs/43721747855) observed MeshHarbor-issued signatures and successful fresh verification on Linux, macOS, and Windows. The original Windows native job's repeated materials check nevertheless failed before execution; the later read-only [Windows run #43731453754](https://github.com/syi0808/meshharbor/actions/runs/43731453754) verified and executed the same original Windows artifact, without creating a new signature.


The certificate's `sourceRepositoryDigest` is the MeshHarbor workflow-source commit, not the pinned QuadriFlow upstream commit. The in-process verifier binds the signed SLSA materials to both commits, the checked-in build recipe, workflow identity, run/attempt, and executable digest. It requires the immutable GitHub OIDC subject `repo:syi0808@66503450/meshharbor@1454899411:ref:refs/heads/main`; the pinned upstream Sigstore conda fixture predates Fulcio's subject extension and uses an explicit test-only policy that accepts only that fixture's missing extension. The candidate run [#43721747855](https://github.com/syi0808/meshharbor/actions/runs/43721747855) produced MeshHarbor-issued certificates accepted by its fresh verification jobs on all three OSes. The original Windows native job still failed its separate materials recheck before execution; a read-only [Windows verification run #43731453754](https://github.com/syi0808/meshharbor/actions/runs/43731453754) later accepted the same original artifact. This run evidence applies to that exact workflow and candidate only; the offline fixture does not prove general build reproducibility, complete native dependency inventory, or legal clearance. The empty product manifest and disabled installer gate stay in place.

The resulting files are candidate evidence only. `provenance.json` is diagnostic build metadata, and `verification.json` is a local verifier summary, not a second signature. The candidate-status file remains `installable=false`, `release_ready=false`, and `dependency_closure_verified=false`. In particular, this candidate workflow does not produce a complete SBOM or reviewed dependency notices. The product verifier is integrated, but the release manifest stays empty and installer requests remain unavailable until a complete, reviewed package passes all independent release gates.

## Exact signed-artifact acceptance still required

The candidate workflow retains its `--build-only` build jobs; the isolated signer attests a primary executable only after its independent build has the same digest. Candidate run [#43721747855](https://github.com/syi0808/meshharbor/actions/runs/43721747855) provides actual evidence for that workflow: the common gate accepted all three byte-identical primary/independent pairs, each platform's signer and fresh verifier passed, and Linux/macOS native jobs executed the same signed digests against the synthetic cube. Their passing jobs also ran MeshHarbor's core geometry-output validator. Linux captured `readelf -d` and `readelf --version-info` diagnostics without installing analysis tools. The original Windows native job's second SLSA-material check failed before running the candidate; the later read-only [run #43731453754](https://github.com/syi0808/meshharbor/actions/runs/43731453754) verified the original signed Windows artifact and executed its native cube smoke, but did not run the MeshHarbor core geometry validator. Environment filtering is not an OS sandbox and does not isolate the binary from its ephemeral runner account or network. All smoke inputs were geometry-only synthetic cubes; no textured GLB or visual-appearance acceptance was tested. Signed candidate ZIPs from run #43721747855 were configured for one-day retention; verification and smoke-evidence artifacts were configured for seven days. The exact candidate run created public attestation metadata. None of these temporary results is a release or product install capability.

A clean install cannot currently be exercised through the production installer. The embedded product manifest is empty, the public installer rejects before network or filesystem I/O, and this candidate workflow does not produce a reviewed complete install archive. Temporary Actions artifacts and verifier summaries are not installer capabilities. Do not add a product-manifest override or use test-only manifest injection to claim a product clean install. Before any release record, a reviewed validation path must:

1. Build and review the complete USTAR package from the native-smoke-tested executable, complete third-party notices, and independently validated SBOM. Record exact archive and payload sizes/digests in a reviewed manifest, then test a clean install into an isolated empty data directory using that exact archive. Verify status becomes ready only after installation, execute the operation, and check installed payload and rollback.
2. Keep geometry-only and textured acceptance distinct. In addition to the cube smoke, run a deterministic closed, static, single-primitive/single-material GLB fixture with embedded PNG base-color and metallic-roughness maps through the native executable. Verify that the separate OBJ contains editable quad faces and no UV/material records, while the GLB preview is triangulated, retains both rebaked maps, and reports projection coverage. A fixture result validates only this narrow supported contract; it is not evidence of general texture quality.

The existing fixture-runner unit tests exercise the core's GLB-to-OBJ-input, output validation, preview, and report path without a native binary. They do not run the packaged executable, verify a signed artifact, install an archive, or establish visual fidelity. A MeshHarbor-issued signed candidate and exact-signed-digest smoke evidence now exist for the narrow synthetic-cube checks described above. A separate private Linux pilot ([#39](https://github.com/syi0808/meshharbor/pull/39)) used the exact signed executable with a supported textured GLB and a test-only runner, not an installed package. This is one supported-fixture result, not a packaged or cross-platform acceptance check. No clean install using a production release manifest has been performed. The product manifest must remain empty until public-attestation, package, dependency-closure, license-review, and release-approval gates are independently complete.

Action references in the candidate and reusable build workflows are pinned to immutable commits: checkout v4.2.2 (`11bd71901bbe5b1630ceea73d27597364c9af683`), setup-python v5.6.0 (`a26af69be951a213d495a4c3e4e4022e16d87065`), attest v4.2.2 (`1e69f48acb82d1966a394da916b4c1698aa569d6`), upload-artifact v4.6.2 (`ea165f8d65b6e75b540449e92b4886f43607fa02`), and download-artifact v4.3.0 (`d3f86a106a0bac45b974a628896c90dbdf5c8093`). The source commit and build flags are fixed. Hosted runner images and apt/Homebrew/vcpkg dependency state are still mutable and are recorded only as diagnostics. The two-build check is a fail-closed guard against a single candidate artifact being substituted with bytes that do not reproduce from the same checked-in recipe; it is not a hermetic reproducible-build guarantee or an independent cryptographic attestation from each builder. It also cannot protect against a compromised workflow/source change, compromised GitHub Actions control plane, or both build jobs being compromised. The common pre-sign gate in run #43721747855 did establish that each platform's two selected candidate artifacts matched byte-for-byte for that run. This is evidence for those exact outputs, not a hermetic reproducible-build guarantee; a future mismatch must still block signing rather than be worked around. Full dependency closure and platform packaging remain release blockers.

## Local USTAR assembly round-trip (not a release)

`scripts/quadriflow_ustar_package.py` assembles the installer's exact five-file payload into an uncompressed POSIX USTAR archive. It accepts only a caller-provided directory containing the platform executable plus `THIRD-PARTY-NOTICES.md`, `sbom.spdx.json`, `provenance.json`, and `provenance.sigstore.json`; it rejects symlinks, missing or extra files, empty payloads, and an existing output path. It fixes owner, mode, and timestamp metadata for deterministic archive bytes and prints the archive size and SHA-256. It does not build or execute QuadriFlow, verify the signature or SBOM, establish dependency closure/license clearance, update the product manifest, or make an archive installable. Its `installable`, `release_ready`, and `dependency_closure_verified` report fields remain false.

The local/CI contract test creates only synthetic fixture data, runs the archive recipe twice, and passes the resulting bytes through `install_manifest_with_fetcher` and the same Rust USTAR parser used by the installer. It verifies the extracted executable and all four metadata payloads against their source bytes. The parser is invoked through a test-only manifest capability and a local fake fetcher; no network access, signature validation, release manifest override, sidecar execution, or product clean-install claim is involved. `retopology-worker.yml` already discovers this test with its `test_quadriflow_*.py` Python unittest suite.

Run this isolated round-trip locally with:

```sh
python3 -m unittest scripts.test_quadriflow_ustar_package
```

The checked-in fixture files explicitly say they are synthetic and are not an executable, third-party notices, or valid signature. A production archive still requires reviewed, exact payloads and release approvals; this test is only an assembly/parser contract check while the bundled manifest remains empty.

## Notice/SBOM evidence helper

`scripts/quadriflow_notices.py` is an offline, Python standard-library-only tool. It accepts a caller-supplied inventory and writes to a new output directory:

- Original, byte-preserved notice files under `third-party-notices/<package-id>/`.
- `THIRD-PARTY-NOTICES.md` index and `notice-inventory.json`.
- SPDX 2.3-shaped `sbom.spdx.json` plus `SHA256SUMS` (which excludes its own checksum).

Example inventory (use only after checking the actual source checkout and installed package versions):

```json
{
  "source_commit": "810b7a0967c35b0dc85b4464e3835e26a756c967",
  "packages": [{
    "id": "quadriflow",
    "name": "QuadriFlow",
    "version": "810b7a0967c35b0dc85b4464e3835e26a756c967",
    "manager": "source",
    "root": "/canonical/real/checkout",
    "notices": ["LICENSE.txt"],
    "license_declared": "NOASSERTION"
  }]
}
```

Run it with an explicit stable epoch and a destination that does not exist:

```sh
OUT=$(python3 -c 'from pathlib import Path; print(Path("/tmp").resolve() / "qf-notices")')
python3 scripts/quadriflow_notices.py inventory.json "$OUT" --source-date-epoch 1760000000
```

The source revision field is a caller assertion; the tool does not inspect Git. It requires each dependency to be listed explicitly with its installed version and reviewed notice paths. Candidate discovery for source/Homebrew is bounded; apt/vcpkg adapters use explicit package names and conventional copyright paths. It never queries a package manager, fetches license text, resolves dependency closure, or makes license conclusions.

Inputs and files are bounded (512 packages/notices, 4 MiB per notice, 16 MiB total notice bytes, 20,000 candidate scan entries). It rejects symlinks, traversal, control characters, binary/empty content, nonportable names, and case-insensitive output collisions. It creates a new output directory exclusively and does not overwrite one. Output parents and inventory roots must be canonical real directories; on macOS, resolve the `/tmp` alias before using it. Deterministic JSON/checksum content uses the supplied timestamp; directory metadata and native compiler outputs are not normalized, so this does not make the overall build reproducible.

For an archive-layout rehearsal, pass `--archive-evidence` to additionally create `archive-evidence/THIRD-PARTY-NOTICES.md` and `archive-evidence/sbom.spdx.json`. The first embeds the original notice bytes with boundaries, sizes, and hashes; the second references only the combined notice file actually present in the five-payload USTAR layout, not the loose review-tree files. These optional payloads are capped at the installer's 8 MiB notice and 16 MiB SPDX limits. The standard review-tree files remain separate. Use only the archive-evidence pair, not the review-tree index and SPDX, when rehearsing that archive layout.

The helper intentionally records `release_ready=false` and `dependency_closure_verified=false`. Its SPDX-shaped output is not checked by an external SPDX validator, license-expression grammar is not fully parsed, and no legal approval is implied. A release pipeline must review the actual linked dependency closure and independently validate the SPDX output.

## Reproducibility and release gates

The older smoke workflow installs native dependencies from moving apt, Homebrew, and vcpkg state and uses version-tag action references. The manual candidate workflow pins its actions and Python version, but native compiler/dependency state and hosted runner images remain mutable. Recorded tool/package versions are diagnostic, not lockfiles. A release pipeline therefore still needs pinned compiler/CMake versions, a pinned vcpkg baseline or exact formula/package snapshots, a pinned Linux image and packages, deterministic archive creation, and repeat builds with matching hashes before it can claim reproducibility.

The source notice scan does not prove the complete per-platform dependency closure, including compiler runtime libraries and linked native packages. Complete notice collection, independently validated SBOMs, provenance/signature verification, and legal review are still release gates. No project-level license is selected here.
