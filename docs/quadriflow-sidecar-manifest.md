# QuadriFlow sidecar manifest and installer

The checked-in manifest, `registry/backends/quadriflow.json`, is intentionally empty. CLI, REST, MCP, and Studio expose QuadriFlow backend status plus a guarded install request, but this build has no released artifact and no in-build release-signature/provenance verifier. A separate manual candidate workflow can attest a temporary executable and verify the attestation for maintainer review; it does not enable installation. The request returns a precise unavailable result before creating the QuadriFlow backend directory, invoking a downloader, or making a network request. The engine still creates its normal local data-store directories when it starts. Temporary Actions artifacts are never accepted as installer inputs.

The core contains a fail-closed installer mechanism built on existing workspace crates plus host OS `curl`; it adds no downloader/archive dependency. Current user-facing install routes cannot reach its downloader until a reviewed signed release and an in-build signature/provenance verifier are available. It accepts only the fixed upstream source pin and MeshHarbor GitHub Releases URLs already constrained by the manifest validator. It requires HTTPS for redirect hops, checks the final effective URL against an exact GitHub release asset-host allowlist, bounds transfer time/size, and verifies the archive SHA-256 and exact byte length against the application-bundled manifest before parsing it.

Packages use uncompressed POSIX USTAR on all three tested targets. Extraction accepts only the platform's executable plus these exact files: `THIRD-PARTY-NOTICES.md`, `sbom.spdx.json`, `provenance.json`, and `provenance.sigstore.json`, with an optional empty `bin/` directory header. It rejects path traversal, absolute/backslash paths, duplicates, links, PAX/GNU extensions, special entries, non-USTAR headers, bad checksums, malformed sizes, missing/extra members, bad padding, and any payload size/hash mismatch. Archive modes are ignored. The executable receives owner-only execute permissions, other files remain owner-only, and installer data directories are private on Unix. Windows uses the inherited ACL on the per-user MeshHarbor data directory; no elevation or global install path is requested.

Installation writes an immutable version directory on the same volume, then atomically creates a new activation marker in the same directory. The previous marker and version remain available for rollback; stale locks fail closed and require manual cleanup rather than being guessed stale. Archive extraction, versioning, activation, and rollback have fake-downloader tests; tests do not use the network or run QuadriFlow. The running operation path can resolve the managed sidecar from the selected MeshHarbor data directory.

Important trust boundary: SHA-256 verifies exact bytes against the manifest committed with the application. This code does **not** cryptographically verify the Sigstore bundle, validate the provenance claims, prove the SBOM/dependency closure, or establish license clearance. A nonempty manifest is not by itself legal or supply-chain approval. Those are release gates; this empty manifest does not enable downloading, installation, or execution.

The manifest format is documented in [the JSON schema](../schemas/quadriflow-release-manifest.schema.json). The notice/SBOM evidence helper and its limitations are in [the packaging notes](quadriflow-sidecar-packaging.md).
