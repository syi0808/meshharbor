# QuadriFlow sidecar manifest and installer

The checked-in manifest, `registry/backends/quadriflow.json`, is intentionally empty. CLI, REST, MCP, and Studio expose QuadriFlow backend status plus a guarded install request, but this build has no released artifact. The in-build verifier now checks a manifest-pinned Sigstore bundle offline before installation can touch disk or start a downloader. Because the manifest is empty, the request still returns a precise unavailable result before creating the QuadriFlow backend directory or making a network request. The engine still creates its normal local data-store directories when it starts. Temporary Actions artifacts are never accepted as installer inputs.

The core contains a fail-closed installer mechanism using host OS `curl`; it adds no downloader/archive dependency. User-facing install routes can reach its downloader only after the bundled manifest has passed the in-process Sigstore and provenance verifier. It accepts only the fixed upstream source pin and MeshHarbor GitHub Releases URLs already constrained by the manifest validator. It requires HTTPS for redirect hops, checks the final effective URL against an exact GitHub release asset-host allowlist, bounds transfer time/size, and verifies the archive SHA-256 and exact byte length against the application-bundled manifest before parsing it.

Packages use uncompressed POSIX USTAR on all three tested targets. Extraction accepts only the platform's executable plus these exact files: `THIRD-PARTY-NOTICES.md`, `sbom.spdx.json`, `provenance.json`, and `provenance.sigstore.json`, with an optional empty `bin/` directory header. It rejects path traversal, absolute/backslash paths, duplicates, links, PAX/GNU extensions, special entries, non-USTAR headers, bad checksums, malformed sizes, missing/extra members, bad padding, and any payload size/hash mismatch. Archive modes are ignored. The executable receives owner-only execute permissions, other files remain owner-only, and installer data directories are private on Unix. Windows uses the inherited ACL on the per-user MeshHarbor data directory; no elevation or global install path is requested.

Installation writes an immutable version directory on the same volume, then atomically creates a new activation marker in the same directory. The previous marker and version remain available for rollback; stale locks fail closed and require manual cleanup rather than being guessed stale. Archive extraction, versioning, activation, and rollback have fake-downloader tests; tests do not use the network or run QuadriFlow. The running operation path can resolve the managed sidecar from the selected MeshHarbor data directory.

The manifest embeds the exact base64 Sigstore bundle bytes so the verifier does not need to fetch an attestation before deciding whether to download a package. It requires the public-good trust root, exact workflow SAN and OIDC issuer, certificate/SCT/Rekor verification and an authenticated timestamp, matching GitHub Fulcio CI claims, and a single SLSA v1 subject whose digest equals the pinned executable. The MeshHarbor policy also requires the exact immutable GitHub OIDC subject `repo:syi0808@66503450/meshharbor@1454899411:ref:refs/heads/main`, which follows GitHub's default subject format for repositories created after July 15, 2026 ([GitHub OIDC reference](https://docs.github.com/en/actions/reference/security/oidc)). A custom repository subject template would therefore be rejected until separately reviewed and pinned. The upstream historical conda regression fixture predates Fulcio's token-subject certificate extension, so only that fixture's test policy explicitly requires the extension to be absent; production verification never accepts a missing or mismatched token subject. It also checks the exact workflow run/attempt, repository IDs/ref, pinned QuadriFlow Git commit, MeshHarbor workflow commit, and SHA-256 of the build recipe embedded in this application. Extra or missing materials fail closed. The archive's `provenance.sigstore.json` must match the exact bytes and hash embedded in the app manifest.

Important trust boundary: SHA-256 verifies exact bytes against the manifest committed with the application. Cryptographic provenance does **not** prove the SBOM/dependency closure, establish license clearance, or constitute release approval. The embedded Sigstore public-good trust root is an offline snapshot, so applications need an update to receive newer trust material. A nonempty manifest is not by itself legal or supply-chain approval. Those are release gates; this empty manifest does not enable downloading, installation, or execution.

The manifest format is documented in [the JSON schema](../schemas/quadriflow-release-manifest.schema.json). The notice/SBOM evidence helper and its limitations are in [the packaging notes](quadriflow-sidecar-packaging.md).
