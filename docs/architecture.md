# Architecture and implementation status

## Intended architecture

The approved product direction is a Rust application with Axum/Tokio, Clap, the official `rmcp` Rust SDK, one operation core, SQLite metadata, a file-based artifact store, and a React/TypeScript/Three.js Studio. Model-specific CUDA and MLX workers remain separable backends and may also be vendored in this monorepo. One user entry binary should own REST, CLI, MCP, and the Studio entry point. The system must not imply that an unavailable model runtime is installable or commercially cleared.

## Implemented Rust slice

- `crates/core/src/store.rs` owns SQLite assets, artifacts and job state plus immutable SHA-256-addressed files. Source import creates a new asset; simplification creates a derived asset linked back to its source.
- Artifact reads are bounded to 512 MiB and verified against the recorded byte size and SHA-256. Corrupt or mismatched content fails closed; deduplicated imports validate existing bytes and never silently replace or repair a damaged content-addressed file.
- Every import entry path shares a 512 MiB asset limit. CLI reads at most limit + 1 bytes, the REST asset-upload route enforces its larger body limit while other routes keep Axum's default, and MCP checks Base64 length before allocating decoded bytes. Standalone PNG/JPEG asset files are limited to 16 MiB and 16 megapixels; PNG chunks/checksums and JPEG frame/scan marker structure are checked before storage. Image payloads are not decompressed, so these checks do not certify pixel-stream decodability or image quality. Before generation, both MLX and CUDA use the same bounded on-disk reread, verify the recorded asset and artifact SHA-256 digests, and revalidate the image format, so legacy stored images are checked again before any backend starts.
- `crates/core/src/glb.rs` parses GLB v2 chunks, inspects metadata, and implements meshoptimizer simplification, conservative face cleanup, vertex-cache/overdraw render optimization, and required `KHR_meshopt_compression` output for supported static indexed triangle data. `crates/core/src/parts.rs` groups triangles by shared indices and unambiguous exact seams, emits up to 256 primitives in the same mesh, and groups excess fragments without dropping faces. It does not split scene nodes or retopologize.
- `crates/atlas-baker` and `crates/xatlas-sys` provide a bounded xatlas integration: one supported static mesh/primitive/material, with same-mesh rebaking of embedded base-color and metallic/roughness PNG maps. This is not high-to-low projection; unsupported textures, extensions, tangents, and multi-primitive assets are rejected. Exact vendored-source notices are retained with the xatlas crate.
- `crates/core/src/operation.rs` is the shared operation catalog and `OperationCore` used by every current interface.
- `crates/core/src/runtime.rs` manages the isolated MLX uv/Python environment and NAF conversion; `cuda_runtime.rs` manages an isolated Linux x86_64/NVIDIA PyTorch 2.6.0/CUDA 12.4 environment and runs the upstream CUDA/SDPA setup preflight. Model downloads are explicit separate actions with required confirmation fields. Hugging Face login is available from the masked CLI or same-origin Studio, with a per-backend private cache. Generic REST bearer clients and MCP cannot submit credentials. CUDA upstream lacks a committed lock, so first setup resolves a private per-install lock rather than claiming cross-machine reproducibility.
- `crates/core/src/generation.rs` handles typed requests for `model.generate` and its `image.generate` compatibility path. Profiles advertise supported input modes; TRELLIS Text [MLX](trellis-text-mlx.md) and [CUDA](trellis-text-cuda.md) consume text directly. Workers receive prompts on stdin rather than in arguments or job records. Input staging and worker dispatch are separate from shared GLB validation and storage. Generated assets carry an explicit origin independent of optional source-asset lineage. No backend automatically installs packages or downloads weights during generation.
- `crates/core/build.rs` embeds only the 209 CUDA/MLX source files named in `crates/core/runtime_bundle_manifest.json`. It verifies every file's size and SHA-256 and checks the manifest against a separately pinned digest and count; any additional non-`.pyc` file outside ignored `__pycache__/` directories under the scanned runtime directories fails the build. It compiles staged verified bytes rather than including mutable checkout files. Runtime setup extracts source into application data, so source paths do not depend on the build machine's checkout. This does not bundle `uv`, Python, third-party wheels, or model weights.
- `crates/meshharbor/src/main.rs` provides CLI, loopback REST, one-slot async mesh jobs, and stdio MCP in a single Rust binary. Serve and MCP hold shared OS advisory locks in the data directory, so both interfaces can run together. Per-session advisory locks let startup recover unfinished jobs from dead owners without affecting another live service. Legacy unowned jobs and explicit CLI recovery require exclusive access to the service lock. Pixal3D runtime setup, downloads, Hugging Face login, and conversion use a separate exclusive OS advisory lock; image generation uses a shared lock, so generation can run concurrently with generation but not while managed runtime files or caches are changing. Conflicts fail fast with a retryable message, the OS releases locks when a process exits or crashes, and independent data directories do not block each other. These locks coordinate MeshHarbor processes but are not a security boundary against unrelated processes running as the same OS user. A hard termination during a managed uv/Python command may leave its child running after MeshHarbor exits and the OS releases the lock; verify the child has exited before retrying. The job supervisor terminates tracked worker processes on graceful shutdown, but cannot do so when the parent is force-killed. The built-in dashboard gets tokenless access only with its non-simple marker and exact same-origin browser provenance; tokenless API writes require exact `Origin`. Blank `MESHHARBOR_API_TOKEN` overrides are refused; generated temporary tokens are printed once at startup, while configured values are not logged. Valid bearer-authenticated non-browser REST clients may omit `Origin` for compatibility, but any supplied `Origin` must match the loopback `Host`. The marker is not local-process authentication: same-OS-user processes can forge request headers, which is documented as part of the single-user loopback trust boundary. Served Studio HTML sets `frame-ancestors 'none'` and `X-Frame-Options: DENY`.
- CLI `jobs list`/`jobs show`, REST job reads, MCP `list_jobs`/`get_job`, and Studio history query the same persisted records; lists are bounded to 1–200, show newest updates first, and never resume or modify saved jobs. Explicit interrupted-job recovery remains a separate guarded action.
- `crates/meshharbor/build.rs` validates and embeds the checked-in `apps/studio/dist` files. Cargo does not run Node.js or pnpm.
- `crates/core/src/quadriflow.rs` validates the actual QuadriFlow quad OBJ and creates a triangulated GLB preview; its separate OBJ artifact is retained for editable quad topology. An optional bounded xatlas/BVH rebake projects only supported embedded base-color and metallic/roughness PNG maps from one constrained source mesh onto the retopologized preview. A 2%-of-source-bounds distance cap, similar-facing-normal gate, 99.5% coverage floor, thin-shell ambiguity rejection, and input/output limits fail closed. This does not prove visual fidelity or eliminate self-intersections and measured surface error.
- `apps/studio/` contains a React/TypeScript/Three.js source client for importing/previewing GLBs and PNG/JPEG inputs, starting/polling simplify, cleanup, UV-rebake, render-optimization, compression, and conditional QuadriFlow retopology jobs, MLX/CUDA runtime setup/download jobs, backend selection, image-generation jobs, and downloading results. Retopology is available in an [opt-in linked build](retopology-candidate.md#linked-development-build) or with a signature-verified, manifest-matched managed release. The default manifest is empty, and adjacent executables are ignored. It connects automatically without asking for a token. Studio is built with pnpm and checked in. The frontend CI rebuilds it from the lockfile and checks for a diff; separate package smoke jobs build the binary from the checked-in bundle on Linux, macOS, and Windows.
- `meshopt` 0.7.0 supplies the Rust wrapper and builds meshoptimizer's C++ implementation as a normal dependency. There is no bespoke C++ worker and no copied `glb-mesh-refiner` core in the active product tree.

## Scope boundaries and incomplete work

The current code is a tested product-core slice, not the whole planned product:

- The embedded Studio startup smoke builds the release-mode CLI from the checked-in bundle on pinned Ubuntu 24.04, macOS 15, and Windows Server 2022 runners. The smoke checks the health endpoint and serves the embedded HTML/JS/CSS; a separate Linux Chromium test checks one generated textured GLB workflow. Neither check covers broader browser or real-asset visual QA, an installer, code signing, or a published release package. There is no desktop shell. See [the embedded Studio build and smoke guide](embedded-studio-package-smoke.md).
- Image-to-3D shares the core across Studio, CLI, REST jobs, and MCP. A [local MLX validation run](pixal3d-mlx-manual-runtime.md#validation-status) verified fresh uv/Python setup, NAF conversion, actual offline GPU generation, and Studio optimization, comparison, and export on one Apple Silicon Mac. It reused the large checkpoints rather than redownloading them. Gated DINOv3 access must be obtained by the user, downloads require explicit consent, and model/checkpoint terms remain separate from the MIT source notices. CUDA setup is Linux x86_64/NVIDIA only and has no fresh current-source GPU validation or committed complete dependency lock.
- The operation catalog exposes cleanup, renderer-order optimization, required mesh compression, bounded xatlas UV rebaking, and an experimental QuadriFlow adapter. The linked development build runs the C++ solver in a child invocation of the same MeshHarbor executable. Default builds only accept a verified managed sidecar and do not ship an approved sidecar. It accepts one closed static indexed triangle GLB. Geometry-only input uses POSITION-only geometry; the narrow textured path additionally requires UVs and supported embedded base-color/metallic-roughness PNG maps with optional normals. It preserves output quad topology in a separate geometry-only OBJ and creates a triangulated GLB preview; the preview rebakes only those supported maps through bounded closest-surface projection with distance, normal, coverage, and ambiguity gates. It does not transfer colors, other maps, rigs, or animation and does not certify texture quality, self-intersection freedom, or measured surface error. The separate optional Rust `remesh` crate is an isotropic triangle-remesher prototype, not the `mesh.retopology` implementation. Generic high-to-low texture baking is not implemented.
- Job state persists in SQLite, and `GET /api/v1/jobs?limit=20` plus Studio's recent-job panel expose the newest records. Checking an old record is read-only; it never resumes or restarts work, and a stored queued/running state is not proof that a worker is alive. Graceful shutdown cancels pending jobs, stops running workers at safe checkpoints, and waits for result commits to finish. On startup, dead owners' active jobs are marked failed. REST and Studio can explicitly retry a failed or stopped job as a new record when the input is replayable. Runtime download caches are retained; text prompts are not persisted.
- Separate CI workflows built and attested temporary QuadriFlow candidates and tested synthetic geometry. See [the retopology candidate notes](retopology-candidate.md) for what ran on each platform. These checks are not real-asset visual QA and do not produce a product installer.

The Rust workspace at `e51a76ad` passed the GitHub Actions formatting, strict Clippy, full workspace tests, and Rust 1.88 minimum-version tests. The source smoke matrix has passed synthetic cube smoke on Linux, macOS ARM64, and Windows x64. The separate embedded-Studio smoke builds and starts the release-mode CLI on all three desktop OS runners and verifies local health plus embedded web assets. These checks do not provide a signed installer/release package, broad browser/visual UI QA, or real-asset texture-quality validation.

## Simplification and UV/baking boundary

The product simplification path uses meshoptimizer with border locking and weighted `NORMAL` / `TEXCOORD_0` metrics when those accessors are compatible. It keeps original UVs, vertex buffers, materials, and embedded textures, so no atlas or texture rebake is needed. The triangle limit applies to the sum of all primitives in the GLB. The engine can redistribute the budget between primitives; if it cannot meet the limit without dropping a primitive or exceeding the error tolerance, the job fails without creating a derived asset.

Cleanup removes defective faces first, then tries the same simplifier on eligible primitives without a triangle target, using a fixed meshoptimizer error tolerance of `0.001`. It retains the cleaned indices if simplification cannot safely reduce them. Blended primitives, opposite-winding duplicate faces, and vertex attributes outside the supported error metric bypass this second pass. The measured error is an estimate, not a visual-equivalence guarantee.

The product uses a distinct `crates/atlas-baker` xatlas integration and does not include the experimental `glb-mesh-refiner` implementation. The `uv.unwrap` operation is callable through REST, CLI, MCP, and Studio; it has a one-static-primitive/one-material contract and only embedded base-color plus metallic/roughness rebaking from the same mesh's existing UVs. The textured retopology preview has its own internal, gated projection path. Neither path transfers arbitrary maps or certifies production visual quality. The worker remains bounded and rejects unsupported GLBs; broader fixture and target-renderer acceptance is still required.

## Planned structure

```text
apps/studio/               # React / TypeScript / Three.js source, pnpm lockfile, and checked-in dist bundle
crates/meshharbor/          # one CLI/API/MCP/Studio-serving binary
crates/core/                # operation core, assets, jobs, storage
native/                     # only independently validated C/C++ dependencies
runtimes/pixal3d/cuda/       # pinned source plus managed Linux/NVIDIA CUDA runtime manifest
runtimes/pixal3d/mlx/        # pinned source, embedded by core and used by managed setup
registry/models/             # explicit installability and license status
docs/pixal3d-source-inventory.json # pinned upstream file hashes and exact exclusions
```

Optional future integrations must preserve build/runtime boundaries and licensing; adding a source tree does not make its dependency and model path installable.
