# Architecture and implementation status

## Intended architecture

The approved product direction is a Rust application with Axum/Tokio, Clap, the official `rmcp` Rust SDK, one operation core, SQLite metadata, a file-based artifact store, and a React/TypeScript/Three.js Studio. Model-specific CUDA and MLX workers remain separable backends and may also be vendored in this monorepo. One user entry binary should own REST, CLI, MCP, and the Studio entry point. The system must not imply that an unavailable model runtime is installable or commercially cleared.

## Implemented Rust slice

- `crates/core/src/store.rs` owns SQLite assets, artifacts and job state plus immutable SHA-256-addressed files. Source import creates a new asset; simplification creates a derived asset linked back to its source.
- `crates/core/src/glb.rs` parses GLB v2 chunks, inspects metadata, and implements meshoptimizer simplification, conservative face cleanup, vertex-cache/overdraw render optimization, and required `KHR_meshopt_compression` output for supported static indexed triangle data. `crates/core/src/parts.rs` groups triangles by shared vertex-index connectivity and emits multiple primitives within the same mesh; it does not split scene nodes or retopologize.
- `crates/atlas-baker` and `crates/xatlas-sys` provide a bounded xatlas integration: one supported static mesh/primitive/material, with same-mesh rebaking of embedded base-color and metallic/roughness PNG maps. This is not high-to-low projection; unsupported textures, extensions, tangents, and multi-primitive assets are rejected. Exact vendored-source notices are retained with the xatlas crate.
- `crates/core/src/operation.rs` is the shared operation catalog and `OperationCore` used by every current interface.
- `crates/core/src/runtime.rs` manages the isolated MLX uv/Python environment and NAF conversion; `cuda_runtime.rs` manages an isolated Linux x86_64/NVIDIA PyTorch 2.6.0/CUDA 12.4 environment and runs the upstream CUDA/SDPA setup preflight. Model downloads are explicit separate actions with required confirmation fields. Hugging Face login uses the official masked CLI in a per-backend private cache, never the Studio/REST/MCP. CUDA upstream lacks a committed lock, so first setup resolves a private per-install lock rather than claiming cross-machine reproducibility.
- `crates/core/src/generation.rs` routes the shared `image.generate` flow to `auto`, MLX, or CUDA, runs inference offline, validates the resulting GLB, and imports a derived asset. No backend automatically installs packages or downloads weights during generation.
- `crates/core/build.rs` embeds both pinned upstream source snapshots plus the first-party CUDA adapter manifest in the Rust executable. Runtime setup extracts source into application data, so source paths do not depend on the build machine's checkout. This does not bundle `uv`, Python, third-party wheels, or model weights.
- `crates/meshharbor/src/main.rs` provides CLI, loopback REST, one-slot async mesh jobs, and stdio MCP in a single Rust binary. Serve and MCP hold shared OS advisory locks in the data directory, so both interfaces can run together. Interrupted-job recovery takes the same lock exclusively and cannot mark work failed while either service is active. The lock coordinates MeshHarbor processes but is not a security boundary against another process running as the same OS user. The built-in dashboard gets tokenless access only with its non-simple marker and exact same-origin browser provenance; tokenless API writes require exact `Origin`. Valid bearer-authenticated non-browser REST clients may omit `Origin` for compatibility, but any supplied `Origin` must match the loopback `Host`. The marker is not local-process authentication: same-OS-user processes can forge request headers, which is documented as part of the single-user loopback trust boundary. Served Studio HTML sets `frame-ancestors 'none'` and `X-Frame-Options: DENY`.
- `crates/meshharbor/build.rs` embeds `apps/studio/dist` into that binary when a client build exists; otherwise the root route returns a local not-built notice.
- `crates/core/src/quadriflow.rs` validates the actual QuadriFlow quad OBJ and creates a triangulated GLB preview; its separate OBJ artifact is retained for editable quad topology. An optional bounded xatlas/BVH rebake projects only supported embedded base-color and metallic/roughness PNG maps from one constrained source mesh onto the retopologized preview. A 2%-of-source-bounds distance cap, similar-facing-normal gate, 99.5% coverage floor, thin-shell ambiguity rejection, and input/output limits fail closed. This does not prove visual fidelity or eliminate self-intersections and measured surface error.
- `apps/studio/` contains a React/TypeScript/Three.js source client for importing/previewing GLBs and PNG/JPEG inputs, starting/polling simplify, cleanup, part-separation, render-optimization, compression, and conditional QuadriFlow retopology jobs, MLX/CUDA runtime setup/download jobs, backend selection, image-generation jobs, and downloading results. The low-level `uv.unwrap` operation is intentionally not a standalone Studio tool. The retopology control is enabled only after an in-process signature/provenance verifier accepts a managed release and its executable digest matches the trusted manifest; adjacent executables are ignored. An in-process verifier is integrated, but the manifest is empty, so the control remains unavailable. It connects automatically without asking for a token. The source is present, but npm dependencies were unavailable offline, so the bundle and browser workflow have not been validated.
- `meshopt` 0.7.0 supplies the Rust wrapper and builds meshoptimizer's C++ implementation as a normal dependency. There is no bespoke C++ worker and no copied `glb-mesh-refiner` core in the active product tree.

## Scope boundaries and incomplete work

The current code is a tested product-core slice, not the whole planned product:

- Studio source and a loopback static-serving/embed path exist, but the npm build, embedded production bundle, and browser workflow have not been validated. There is no desktop shell.
- Image-to-3D code is wired through Studio, CLI, REST jobs, and MCP. MLX setup is Apple Silicon only; CUDA setup is Linux x86_64/NVIDIA only. Neither setup nor actual inference has been run end-to-end in this executor. Gated DINOv3 access must be obtained by the user, model downloads require explicit consent, and unresolved model/checkpoint terms remain separate from the MIT source notices. The CUDA route is experimental, with no fresh current-source GPU validation or committed complete dependency lock.
- The operation catalog exposes cleanup, connected-part separation, renderer-order optimization, required mesh compression, low-level bounded xatlas UV rebaking, and an experimental QuadriFlow adapter. The low-level `uv.unwrap` operation remains available through REST, CLI, and MCP but is not a standalone Studio tool. The adapter is unavailable in the current build: adjacent `quadriflow` executables are ignored, and an in-process signature/provenance verifier is integrated, but the empty trusted manifest keeps the adapter unavailable. The repository does not bundle or auto-download an approved binary. It accepts one closed static indexed triangle GLB. Geometry-only input uses POSITION-only geometry; the narrow textured path additionally requires UVs and supported embedded base-color/metallic-roughness PNG maps with optional normals. It preserves output quad topology in a separate geometry-only OBJ and creates a triangulated GLB preview; the preview rebakes only those supported maps through bounded closest-surface projection with distance, normal, coverage, and ambiguity gates. It does not transfer colors, other maps, rigs, or animation and does not certify texture quality, self-intersection freedom, or measured surface error. The separate optional Rust `remesh` crate is an isotropic triangle-remesher prototype, not the `mesh.retopology` implementation. Generic high-to-low texture baking is not implemented.
- Persistent job states exist. After an unexpected exit, the operator can stop every REST/MCP process using the same data directory and run `meshharbor jobs recover-interrupted --confirm-no-running-meshharbor` to mark nonterminal jobs as failed. This explicit command does not resume work or delete assets/download caches; inspect existing assets before retrying. Native C++ simplification, runtime installation, downloads, and model inference cannot currently be interrupted safely once started.
- Earlier CI runs built the pinned QuadriFlow source and ran a synthetic-cube smoke; their status is recorded in [the retopology candidate notes](retopology-candidate.md). The new manual candidate workflow builds and attests temporary candidates but does not execute QuadriFlow, has not been dispatched, and is not a MeshHarbor release build or product installer. Neither flow is real-asset visual QA or validated image-to-output inference.

The Rust workspace at `e51a76ad` passed the GitHub Actions formatting, strict Clippy, full workspace tests, and Rust 1.88 minimum-version tests. The source smoke matrix has passed synthetic cube smoke on Linux, macOS ARM64, and Windows x64. These checks do not make this a complete M1 release or validate MeshHarbor packaging, the UI, or real-asset texture quality on all desktop platforms.

## Simplification and UV/baking boundary

The product simplification path uses meshoptimizer with border locking and weighted `NORMAL` / `TEXCOORD_0` metrics when those accessors are compatible. It keeps original UVs rather than automatically generating a new atlas. Because the current operation does not change vertex buffers, UVs, material definitions, or embedded texture bytes, it does not need xatlas or texture rebaking. The target triangle count is a goal, not a guarantee; material/primitive boundaries and error limits can leave the output above the requested target.

The product uses a distinct `crates/atlas-baker` xatlas integration and does not include the experimental `glb-mesh-refiner` implementation. The low-level `uv.unwrap` operation is callable through REST, CLI, and MCP, not exposed as a standalone Studio button; it has a one-static-primitive/one-material contract and only embedded base-color plus metallic/roughness rebaking from the same mesh's existing UVs. The textured retopology preview has its own internal, gated projection path. Neither path transfers arbitrary maps or certifies production visual quality. The worker remains bounded and rejects unsupported GLBs; broader fixture and target-renderer acceptance is still required.

## Planned structure

```text
apps/studio/               # React / TypeScript / Three.js source; npm build/browser QA pending
crates/meshharbor/          # one CLI/API/MCP/Studio-serving binary
crates/core/                # operation core, assets, jobs, storage
native/                     # only independently validated C/C++ dependencies
runtimes/pixal3d/cuda/       # pinned source plus managed Linux/NVIDIA CUDA runtime manifest
runtimes/pixal3d/mlx/        # pinned source, embedded by core and used by managed setup
registry/models/             # explicit installability and license status
docs/pixal3d-source-inventory.json # pinned upstream file hashes and exact exclusions
```

Optional future integrations must preserve build/runtime boundaries and licensing; adding a source tree does not make its dependency and model path installable.
